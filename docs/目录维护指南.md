# 目录维护指南

本项目把发现、审核和发布分开。自动采集只更新维护材料；正式目录仍通过 `data/catalog.json`、`data/guides.json` 的 PR 审核发布。

## 1. 离线演示

以下固定样例是合成测试数据，代表 API 分页或 HTTP 响应格式，不是真实 MCP 项目，不会加入网站目录。

```sh
npm run registry:sync -- --fixture tests/fixtures/registry-pages.json
npm run registry:sync -- --fixture tests/fixtures/registry-pages.json

npm run check:links -- --fixture tests/fixtures/link-responses.json --catalog tests/fixtures/link-catalog.json --guides tests/fixtures/link-guides.json
```

Registry 演示默认写入 `.maintenance/demo-registry`，链接演示写入 `.maintenance/demo-links`。再次导入相同内容时，报告应显示 0 项内容变化。

测试样例不允许使用 `--export-review`，避免把演示数据当作真实的收录建议导出。

## 2. 官方 Registry 候选导入

```sh
npm run registry:sync
```

来源固定为 `registry.modelcontextprotocol.io/v0.1/servers`。不接受任意用户指定的 API 地址。默认读取 latest 版本，并包含上游显式删除事件。

本地输出目录 `.maintenance/registry` 中：

- `current.json`：指向最新完整批次；不是半完成分页的检查点。
- `runs/<批次>/state.json`：经规范化的上游事实快照与增量水位。
- `runs/<批次>/report.json`：内容变化、待审核状态、关联线索。
- `runs/<批次>/report.md`：便于阅读的摘要。

后续运行会使用前一次完整批次的 `updated_since`。增量水位使用本轮开始前一分钟，保留重叠窗口，重复观察按命名空间去重。游标始终按不透明字符串处理。

分页、格式、游标循环、数量限制、冲突版本或网络失败会中断批次，不推进当前指针。完整扫描没有看见旧记录，也不能推断它已删除。上游 `deprecated` 或 `deleted` 只产生需要人工审核的状态变化。

默认最多 500 页、50000 项观察；需要调整页数时可用 `--max-pages`（上限 1000）。达到上限不会把截断内容当作完整批次。

上游接口并不保证跨页事务快照。重叠窗口和冲突检测降低遗漏风险，不能证明捕获了某一时刻的全量数据；应定期执行完整扫描和人工抽查。

```sh
npm run registry:sync -- --full
```

## 3. 关联已收录项目

`data/registry-bindings.json` 的初始 bindings 为空。只有实际核对命名空间、维护关系及项目范围后才增加关联：

```json
{
  "schemaVersion": 1,
  "bindings": [
    {
      "name": "已核对的 Registry 命名空间",
      "serverId": "现有站内项目 ID",
      "evidence": "https://对应的公开依据"
    }
  ]
}
```

这是结构示意，不能直接用占位符运行。脚本会拒绝无效命名空间、不存在的站内 ID、重复关联或无效证据链接。

仓库及子路径、包标识、远程端点只作为去重线索。单仓库多服务的子路径不同不自动合并，同名项目不自动关联。Registry 发布者身份也不自动等同于对接服务官方身份。

报告中的关联只帮助编辑者定位已有条目，不执行字段覆盖。中文说明、分类、官方身份、费用、指南、测试记录和作者标记都保持由编辑审核。

## 4. 来源链接检查

```sh
npm run check:links
```

检查已发布项目和指南的公开来源链接，去除重复地址；不调用 MCP 端点，不执行安装命令或工具。

| 结果 | 含义 | 编辑动作 |
|---|---|---|
| reachable | 返回成功 HTTP 响应，或成功缓存得到 304 重验证 | 仍须按期核对内容 |
| broken | 404 或 410 | 核对是否迁移、归档或误报，再修改来源 |
| restricted | 401 或 403 | 可能有登录或访问限制，不能直接删项目 |
| rate_limited | 429 | 稍后重试或降低频率 |
| temporary_error | 5xx | 先观察服务恢复情况 |
| unreachable | DNS、连接或超时错误 | 检查运行环境和网络 |
| blocked | URL、私网地址或跳转目标被规则拒绝 | 核对地址，不自动访问 |
| needs_review | 其他未明确分类的响应 | 人工核对 |

优先 HEAD；服务不支持时使用 GET，只检查响应头并丢弃正文。成功响应的 ETag/Last-Modified 可用于下次条件请求。报告保存在 `.maintenance/links/runs`，不会自动写入条目状态。

网络层仅允许公开 HTTPS 地址，拒绝凭证 URL、敏感查询及 IP 字面量。每个请求重新解析并校验地址，连接绑定已校验的公网 IP，TLS 保留原主机校验。每个跳转重新检查，最多三次；限流和临时错误最多尝试三次，并限制等待、正文大小、DNS/请求时间及并发量。

这只是目录来源的 HTTP 检查，不等于内容真实性、MCP 连通性或安全审计。

## 5. 周期报告与可选草稿 PR

`.github/workflows/maintenance.yml` 提供每周一次及手动运行入口：

1. 检查目录源数据。
2. 把官方 Registry 变化导出为维护快照和待审核报告。
3. 检查来源链接。
4. 上传保留 14 天的维护材料。
5. 采集失败时保留可用报告，同时把运行标为失败。

默认不创建 PR。若实际公开仓库的维护者将仓库变量 `MCP_ENABLE_MAINTENANCE_PR` 设为 `true`，并允许 GitHub Actions 创建 PR，则独立的写权限作业会创建或更新 `maintenance/registry-review` 草稿分支。

该分支只提交 `maintenance/registry-state.json` 和 `maintenance/proposals/registry.*`，不提交正式目录，也不自动合并。提案审核合并后，后续运行可从已接受的维护快照开始增量采集。没有内容变化时不会为水位变化单独创建 PR。

尚未配置真实公开仓库，也没有执行远程工作流。本地已提供流程不代表线上任务或 PR 已存在。

## 6. 故障恢复

源站不可达时可以继续使用已发布快照。不要把超时、403 或 DNS 故障改成“项目已下线”。

同一个维护目录只允许一个进程持锁。异常强制中断可能留下 `.lock`；先确认没有相应维护进程，再人工清理锁。脚本不会自动抢占或删除其他进程的锁。

失败批次不更新 `current.json`。已经写完但未被指针选中的 runs 文件夹可供排障；确认不需要后再删除。不要在维护运行时修改当前批次文件。
